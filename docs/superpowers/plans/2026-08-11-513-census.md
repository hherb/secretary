# #513 census — every secret stack slot with a trailing `.zeroize()`

Method: spec §1.2's window test, applied per slot. A script can shortlist
but cannot decide (spec §3.1); every row here is a read judgement, made by
reading the enclosing function (and, where the intervening call is into a
third-party crate — `x25519-dalek`, `ml-kem`, `ml-dsa` — the crate's own
source under `~/.cargo/registry/src/…`, not assumed).

**Scope.** Originally four scan roots: `core/src`,
`ffi/secretary-ffi-bridge/src`, `ffi/secretary-ffi-uniffi/src`,
`ffi/secretary-ffi-py/src`. §3.3's already-confirmed `core/src` rows are
copied here verbatim (Section 1); the brief's explicit "unconfirmed tail" is
Section 2; every remaining real `.zeroize()` call site the raw grep turned up
but neither §3.3 nor the brief's tail named — in every one of the four roots
— is Sections 3-6.

**Scope correction (whole-branch review).** Those four roots are not the
repo, and #513 asked for a repo-wide census. `desktop/src-tauri/src` and
`cli/src` were silently outside every root while CLAUDE.md described the
work as DONE. `cli/src` holds no trailing-wipe site; `desktop/src-tauri/src`
held **two**, both now converted — see **Addendum 3** below for the rows.

The wider lesson is about the census METHOD, not these two sites: a
grep-driven census inherits the blind spots of both its pattern and its
roots. The pattern blind spot cost two never-wiped slots (`generate`'s
`entropy`, and the two `Vec`-typed bundle keys found in the same review);
the root blind spot cost these. Neither is visible from inside the census.

**Categories**, beyond the two the brief's window test produces directly:

- **WINDOW — E1/E2/E3** — needs conversion to `Sensitive::build` /
  `try_build` (or, for a heap `Vec<u8>`/`String`, an equivalent wrapper-typed
  local) per design §2.
- **ADJACENT** — no conversion; left as-is (design §6).
- **TEST-ONLY** — `.zeroize()` called on a value inside `#[cfg(test)]` /
  `#[test]`, exercising a type's `Zeroize` derive itself rather than the
  fill-then-wipe idiom. Listed for reconciliation; excluded from conversion.
  Per the task's ambiguity resolution.
- ~~**ACCESSOR HAND-OUT**~~ — **retired in fix round 1 (2026-08-11).** This
  category existed for exactly four rows (`device.rs:62`, `unlock.rs:38`,
  `record.rs:56`, `record.rs:71`) and none of them survived re-testing — see
  the "Fix round 1" note at the end of this file. Kept here, struck through,
  so a reader who remembers seeing the category in an earlier version of
  this file isn't left wondering where it went.
- **DROP-IMPL** — the `.zeroize()` call is inside a `Drop::drop` body. Drop
  runs on every exit path (return, `?`, and unwind alike — that is the
  mechanism design §5.1's test proves for `Sensitive`, and it holds for any
  type's own `Drop` impl equally), so by construction there is no window to
  analyse.
- **EARLY-WIPE-OF-WRAPPED** — an explicit `.zeroize()` call on a field whose
  declared type is already `Sensitive<T>` (`ZeroizeOnDrop`). The call is a
  defensive early wipe, not the thing standing between a secret and its only
  wipe: the owning struct's `Drop` impl wipes the same bytes on every exit
  this call might miss. Not a window.

## Section 6 — `ffi/secretary-ffi-py/src` — all 37 real call sites

**Revised in fix round 1 (2026-08-11) — see the note at the end of this
file.** All 37 real call sites are now **WINDOW**. Spec §3.2's provisional
"33 windowed" prediction under-counted by exactly the four rows that were
originally classified ACCESSOR HAND-OUT (now retired, see Categories above)
and are reclassified WINDOW below.

Every non-accessor WINDOW row shares one shape: an owned `Vec<u8>`
(sometimes also copied into a `[u8;32]` stack array after an explicit prior
length check) is zeroized at every *known* early-return branch (bad UTF-8,
wrong length) and once more after the bridge call — but the bridge call
itself (`secretary_ffi_bridge::*`, a call into another crate that can panic)
sits between the fill and that last zeroize, so an unwind through it skips
every remaining zeroize for that value in the frame. Each row lists every
line that zeroizes the named slot within its function; the verdict is
WINDOW if *any* of them is reachable only after the panic-risking bridge
call.

The four accessor rows (`device.rs:62`, `unlock.rs:38`, `record.rs:56`,
`record.rs:71`) share a *different* shape, verified against pyo3 0.29.0
source (`~/.cargo/registry/src/…/pyo3-0.29.0/`): the fill is the closure
parameter itself (`v`/`s`, the secret already-decrypted `Vec<u8>`/`String`
handed out by the bridge), and the intervening call — `PyBytes::new(py, &v)`
/ `PyString::new(py, &s)` — is documented by pyo3's own doc comment as
panicking ("Panics if out of memory", `src/types/bytes.rs:76`; the same
applies to `PyString::new`, `src/types/string.rs:178`), and the concrete
path is real: `PyBytes_FromStringAndSize`/`PyUnicode_FromStringAndSize` →
`.assume_owned(py)` → `Bound::from_owned_ptr` (`src/instance.rs:346-350`) →
on a null pointer, `panic_on_null` (`src/instance.rs:2425-2430`) →
`panic!("PyObject pointer is null")`. That is a genuine unwinding panic
between the fill and the zeroize, so the same E1 verdict applies as every
other "call into another module that can panic" row in this census.

## Addendum 2 — `ffi/secretary-ffi-uniffi`'s four secret accessors have no Rust-side wipe at all (found in fix round 1's Finding-2 re-audit)

Mirrors Addendum 1's shape, found on the uniffi side while re-auditing per
Finding 2. **Not a row in the 101-call-site reconciliation** — like
Addendum 1, there is no `.zeroize()` call here to have missed.

`ffi/secretary-ffi-uniffi/src/wrappers/` has exactly four secret-shaped
accessors, one-to-one with ffi-py's four (confirmed by grepping every
`Option<Vec<u8>>`/`Option<String>` return in `wrappers/*.rs` and reading
each — the one extra hit, `vault.rs:46 owner_card_bytes()`, returns the
signed, public Contact Card, not secret key material):

- `wrappers/device.rs:14 DeviceSecretOutput::take_secret`
- `wrappers/identity.rs:60 MnemonicOutput::take_phrase`
- `wrappers/block.rs:103 FieldHandle::expose_text`
- `wrappers/block.rs:106 FieldHandle::expose_bytes`

Each is a one-line forwarder — e.g. `pub fn take_secret(&self) -> Option<Vec<u8>> { self.0.take_secret() }`
— with **no local `.zeroize()` call at all**; the doc comments explicitly
push the obligation across the FFI boundary ("Caller MUST zeroize after
use"). This is structurally *different* from the four ffi-py rows Finding 1
reclassified: ffi-py's rows had an *existing* zeroize call with a panic
sitting in front of it (a window); these four have no zeroize attempt in
this crate to window in the first place.

Tracing where the returned `Vec<u8>`/`String` actually goes (per Finding
2's explicit ask to check uniffi lift/lower/`RustBuffer` construction):
uniffi 0.32.0's generated scaffolding lowers the return value via
`<Vec<u8> as Lower<UT>>::lower` / `<String as Lower<UT>>::lower`
(`uniffi_core-0.32.0/src/ffi_converter_impls.rs`). The UDL declares these
four as `bytes?` / `string?` (`secretary.udl:557,586,1041,1050`), and
`uniffi_core` has no specialised fast path for `Vec<u8>` distinct from the
generic `Vec<T>` — both go through the **generic serialising path**:

```rust
// ffi_converter_impls.rs:341-353 (Vec<T>, used for bytes)
fn write(obj: Vec<T>, buf: &mut Vec<u8>) {
    // TODO: would be nice not to panic here :-/
    let len = i32::try_from(obj.len()).unwrap();
    ...
}
// ffi_converter_impls.rs:145-151 (String)
fn write(obj: String, buf: &mut Vec<u8>) {
    // TODO: it would be nice not to panic here.
    let len = i32::try_from(obj.len()).unwrap();
    ...
}
```

Two findings, reported precisely rather than folded into one verdict:

1. **A real, upstream-acknowledged panic path exists** (`i32::try_from(len).unwrap()`,
   with upstream's own `TODO` comment admitting it), but it is **not
   practically reachable** for these four secrets — it fires only when
   `obj.len() > i32::MAX` (~2 GiB), and a 32-byte device secret or a
   ~200-byte 24-word phrase is nowhere near that threshold. This is the
   same "present in the compiled code, provably unreachable for the actual
   payload size" shape already recorded for `hkdf_sha256_extract_and_expand`'s
   internal `.expect()` (Section 1) — recorded rather than silently waved
   through, consistent with this census's practice elsewhere.
2. **The structurally significant finding is independent of that panic
   path.** `lower(obj: Vec<T>) -> RustBuffer` takes `obj` **by value**: it
   serialises `obj`'s bytes into a *new* buffer and then drops the original
   `Vec<u8>`/`String` — on the **happy path**, with no panic anywhere. Since
   `Vec<u8>`/`String` are not `ZeroizeOnDrop`, that original transient copy
   (the one `take_secret()`/`take_phrase()`/`expose_text()`/`expose_bytes()`
   returned) is freed **unwiped**, unconditionally — not "windowed by a
   panic" but never wiped in Rust at all, matching Addendum 1's class
   exactly rather than the WINDOW class Finding 1's four rows belong to.

**Why this isn't force-classified WINDOW and added to the action list**:
doing so would misrepresent the fix. A WINDOW row's fix is "wrapper-type the
existing local so `Drop` covers the existing zeroize's blind spot." There is
no existing local/zeroize here to wrapper-type — the fix shape is different
(e.g. wiping the returned value immediately after the accessor call, before
handing it to uniffi's generated `lower()`, which lives in code this crate
doesn't own) and needs its own design discussion, not a mechanical
`Sensitive::build` conversion. Recorded as its own addendum instead of
force-fit into WINDOW, per the same "flag ambiguity rather than force a
verdict" discipline applied throughout this census. Filed as **#519** so it
is not lost between this fix round and Task 3-9 — see the "Fix round 1"
note below for the full account of how this was found.

## Fix round 1 (2026-08-11) — what changed and why

A review of this census found two issues and the controller approved a
third, broader re-audit. Full account, so a future reader isn't left
guessing how a wrong classification got into an audit artifact and how it
got fixed:

- **Provenance of the original ACCESSOR HAND-OUT classification.** The
  controller's dispatch prompt for Task 2 pre-classified four specific
  sites (`device.rs:62`, `unlock.rs:38`, `record.rs:56`, `record.rs:71`) as
  "accessor hand-out — different pattern, not a window" (ambiguity
  resolution #2 in that prompt), and this census followed that instruction
  faithfully — the reviewer, seeing only the brief files and not the
  dispatch prompt, read the resulting citation as unsupported and flagged
  it as fabricated. It was not fabricated; it traced to a controller
  instruction the reviewer couldn't see. The controller has since
  determined the instruction itself was a pre-judgement that should have
  been left to the window test, and withdrew it.
- **Finding 1 (critical):** applying the window test properly to those four
  sites — rather than the withdrawn shortcut — finds a genuine, pyo3-source-
  verified panic (`PyBytes::new`/`PyString::new` → `assume_owned` →
  `Bound::from_owned_ptr` → `panic_on_null`) sitting between each site's
  fill and its zeroize. All four reclassified WINDOW — E1 in Section 6
  above, with the category retired since no site remained in it.
- **Finding 2 (approved scope expansion):** re-ran the search for
  pyo3/uniffi FFI-construction-or-conversion calls across the *entirety* of
  `ffi/secretary-ffi-py/src/**` and `ffi/secretary-ffi-uniffi/src/**`, not
  just the four already-named sites. Result: no further ffi-py sites (every
  other `PyBytes::new`/`PyString::new` call touches non-secret data —
  UUIDs, or ciphertext bytes destined for disk — confirmed by reading each
  one's surrounding context and doc comments); no `.into_pyobject`/
  `PyList::new`/`PyByteArray::new`/`from_owned_ptr` calls anywhere in
  ffi-py; no hand-written `RustBuffer`/lift/lower calls in ffi-uniffi's
  source (uniffi's generated scaffolding handles that outside this crate's
  hand-written tree). But the re-audit *did* surface something real and
  worth reporting even though it doesn't fit the WINDOW shape: uniffi's
  four secret accessors have **no** Rust-side zeroize attempt at all, not
  merely a windowed one (Addendum 2, filed as **#519** rather than forced
  into this action list, since its fix shape genuinely differs from a
  `Sensitive::build` conversion).
- **Finding 3 (minor):** `identity_clone.ml_dsa_65_sk`'s field type was
  mis-cited as `Sensitive<[u8;N]>`; corrected to `Sensitive<Vec<u8>>`
  (`core/src/unlock/bundle.rs:208`) in Section 4. The EARLY-WIPE-OF-WRAPPED
  classification was unaffected — both spellings derive `ZeroizeOnDrop`.
- **Net effect on the reconciliation:** 101 real call sites unchanged; 108
  raw grep hits unchanged; WINDOW count 45 → 49; ACCESSOR HAND-OUT 4 → 0
  (category retired); every other category unchanged. See "Reconciliation
  arithmetic" above for the updated table.
