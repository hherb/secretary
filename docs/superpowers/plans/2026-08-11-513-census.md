# #513 census — every secret stack slot with a trailing `.zeroize()`

Method: spec §1.2's window test, applied per slot. A script can shortlist
but cannot decide (spec §3.1); every row here is a read judgement, made by
reading the enclosing function (and, where the intervening call is into a
third-party crate — `x25519-dalek`, `ml-kem`, `ml-dsa` — the crate's own
source under `~/.cargo/registry/src/…`, not assumed).

**Scope.** Four scan roots: `core/src`, `ffi/secretary-ffi-bridge/src`,
`ffi/secretary-ffi-uniffi/src`, `ffi/secretary-ffi-py/src`. §3.3's
already-confirmed `core/src` rows are copied here verbatim (Section 1); the
brief's explicit "unconfirmed tail" is Section 2; every remaining real
`.zeroize()` call site the raw grep turned up but neither §3.3 nor the
brief's tail named — in every one of the four roots — is Sections 3-6.

**Categories**, beyond the two the brief's window test produces directly:

- **WINDOW — E1/E2/E3** — needs conversion to `Sensitive::build` /
  `try_build` (or, for a heap `Vec<u8>`/`String`, an equivalent wrapper-typed
  local) per design §2.
- **ADJACENT** — no conversion; left as-is (design §6).
- **TEST-ONLY** — `.zeroize()` called on a value inside `#[cfg(test)]` /
  `#[test]`, exercising a type's `Zeroize` derive itself rather than the
  fill-then-wipe idiom. Listed for reconciliation; excluded from conversion.
  Per the task's ambiguity resolution.
- **ACCESSOR HAND-OUT** — a value being copied out to the FFI caller (Python
  `bytes`/`str`) is wiped after the copy. Different pattern from a scratch
  fill slot; not analysed as a window. Per the task's ambiguity resolution
  (the brief's own named examples: `device.rs:62`, `unlock.rs:38`,
  `record.rs:56`, `record.rs:71`).
- **DROP-IMPL** — the `.zeroize()` call is inside a `Drop::drop` body. Drop
  runs on every exit path (return, `?`, and unwind alike — that is the
  mechanism design §5.1's test proves for `Sensitive`, and it holds for any
  type's own `Drop` impl equally), so by construction there is no window to
  analyse.
- **EARLY-WIPE-OF-WRAPPED** — an explicit `.zeroize()` call on a field whose
  declared type is already `Sensitive<T>` (`ZeroizeOnDrop`). The call is a
  defensive early wipe, not the thing standing between a secret and its only
  wipe: the owning struct's `Drop` impl wipes the same bytes on every exit
  this call might miss. Not a window.

## Reconciliation

```
grep -rn "\.zeroize()" core/src ffi --include="*.rs" | grep -v "^\s*//" | wc -l
```

prints **108** — but that second `grep -v "^\s*//"` does not do what the
command intends. `grep -rn` prefixes every hit with `path:line:`, so the
pattern `^\s*//` (anchored at the *start of that combined string*) never
matches — no line in `core/src`/`ffi` starts with whitespace or `//`, the
path does. The exclusion is a no-op; all 108 raw hits pass through
unfiltered, comments included. This is corrected here rather than
propagated: read individually, **7 of the 108 lines are comment references**
to `.zeroize()` (doc comments and `//` lines describing the pattern, not
calls), leaving **101 real call sites**. Every one of the 101 is classified
in the table below; the arithmetic is rechecked in the report.
